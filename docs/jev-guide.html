Jev Proof Check

How TypeSafe's Jev model can tell a weighbridge bill from a geotagged truck photo and read the time on each. Covers what Jev is, what it costs, how it takes images, and the test scripts in this project.

The model

What Jev is

Jev is TypeSafe AI's "System One" model, launched in September 2026. A chat model like ChatGPT or Claude writes text. Jev doesn't. You give it something to look at (the state) and a set of named questions, and it returns a typed answer to each one with probabilities. That makes it fast and cheap for classifying, scoring, routing and checking. It can't write or transcribe text.

A chat model

Asked "What time is on this bill?"

"The time in is 03:09:41."

Free-form text. No built-in measure of how sure it is.

Jev

Asked "What hour is the time in?" with options 00–23

choice: "03" confidence: 0.91 probabilities: 03=0.94, 08=0.03, …

One of your options, with a probability for every option. Illustrative numbers.

The four question types

Noul

Is this statement true?

→ probability 0–1
Choice

Which of these options? Up to 255 options.

→ choice, confidence, probabilities
Score

Where on this scale? 2 to 10 ordered levels.

→ score, confidence, probabilities
Box

Where is it in the image? Jev 1.14 only, experimental.

→ box edges

All questions in a request are answered in parallel, so asking twelve questions takes about as long as asking one. You pay only for the extra input tokens.

TypeSafe's own tests put a typical decision at about $0.0004, against $0.0304 for GPT-5.6 Terra. TypeSafe says it can't prove the price isn't subsidized, but expects prices to fall.

Images

How Jev takes images

Image input is an early feature that TypeSafe calls "dreamer-ready": good for prototypes, not yet production quality. The request format and accuracy can change between releases. Three things to know:

  • Turn it on per request. Send the header TypeSafe-Danger-Zone-Images: true. Without it, a request with an image fails with 400.
  • Images go in by reference. Each image is listed once in an assets map under a unique key, such as a UUID. That key is then written wherever the image belongs: in the state, in a question, or in the answer options. The Python SDK does this for you.
  • The API strips all metadata. EXIF, including GPS coordinates and the camera's orientation flag, is removed. A sideways photo has to be rotated in its pixels before sending.
LimitValue
FormatPNG or JPEG still images. Convert HEIC, WebP and GIF first.
Each side280 to 1568 pixels. Images outside this are rejected, not resized.
Each file16 MiB

Our use case

Bill or geotagged photo, and the time on it

The two sample images below show one load: the truck photographed at the plant, and the weighbridge slip for the same truck. The values listed are what a person reads off each image, to compare Jev's answers against.

How check_proof.py reads each image

  1. Open and size the imageApply any camera rotation flag, convert to RGB, and scale the long side to 1568 px, the largest Jev accepts. This makes small print as large as possible.
  2. Ask all twelve questions in one requestWhat kind of image it is, which way its text is turned, and the hour, minute, day and month for both possible layouts (GPS stamp and bill).
  3. Rotate if sideways, and ask againIf Jev says the text isn't upright, the script rotates the image and sends a second request.Your bill takes this path: its text faces right, so it is turned 90° counter-clockwise.
  4. Keep the answers for the kind foundA bill reports time in, time out and date. A geotagged photo reports the stamp's time and date. Anything else is reported as other.
  5. Print each answer with its confidenceAlso prints the two runner-up options and the tokens used, so a weak reading is easy to spot.

Expectations

What Jev can and can't tell you

Should work well

  • Telling a bill from a geotagged photo. The two look very different, and sorting images into categories is a documented use.
  • Spotting a GPS stamp printed on the photo.
  • Detecting a sideways or upside-down image.
  • Flagging weak readings through low confidence, so they can go to a person.

May be shaky

  • Minutes on the bill. The print is small, and these screenshots are low resolution.
  • Telling apart times on a crowded slip with several printed times.
  • Accuracy that changes between model versions while image support is experimental.

Can't do

  • Read GPS data stored in the file. The API removes it, so only a stamp printed on the image counts.
  • Tell whether a stamp is genuine. GPS camera apps can be set to any place and time.
  • Transcribe text such as the address or serial number. Jev only picks from options you give it.

For proof that holds up, check the GPS and time stored in the original photo file on your own server, and use Jev for the visual checks. Screenshots like these don't carry that data; it has to be the original camera file.

Ideas to build on

So far the scripts check each image on its own. The ideas below link the photo and the bill together, and make the readings more reliable. None of them is built yet. Idea 1

Match the photo's time to the bill

What it checks
The photo's GPS-stamp date and time fall within the trip on the bill: on the same date, and between the bill's time in and time out.
Why it helps
A real truck photo could be reused from another day or another trip. If the photo time is outside the bill's window, the two don't belong together.
How it works
Jev already returns all the numbers in check_proof.py. The rest is ordinary code: build a date and time for each, and compare. No extra Jev request, so no extra cost.
def same_trip(photo, time_in, time_out):
    """Each argument is a datetime built from Jev's answers."""
    return time_in <= photo <= time_out
On your samples
03:09Bill: time in
04:09Photo stamp
08:57Bill: time out

Both dated 15/10/2026, and 04:09 is between 03:09 and 08:57. Same trip

  • Check your process first. This rule assumes the truck is weighed once at each end of its trip, and photographed in between. If your trucks are photographed before the first weighing or after the last, the window needs to be wider.
  • Only trust confident readings. If any time Jev read has low confidence, the comparison could be wrong. Send those cases to a person rather than passing or failing them. A starting threshold like 0.8 can be tuned once you have real results.
  • Trips past midnight. Compare full dates and times, not just times. The script currently reads one date from the bill; a trip crossing midnight needs both dates read.
Idea 2

Match the truck number

What it checks
The registration plate on the truck in the photo is the same as the truck number printed on the bill.
Why it helps
A correct-looking photo of a different truck could be paired with the bill. The time check alone won't catch that.
How it works
Jev can't write out the number, but it can compare. Send both images in one request and ask a yes/no (Noul) question. Jev answers with the probability that they match.
response = client.system_one(
    state={"truck_photo": Image(photo_path), "bill": Image.from_pil(upright_bill)},
    questions={
        "same_truck": Noul(instructions=(
            "Is the registration number on the truck in `truck_photo` the same as "
            "the truck number printed on `bill`? Ignore spaces and letter case."
        )),
    },
)
p = response.nouls["same_truck"].noul   # 0 to 1: probability it's the same truck
On your samples

KL05AF9341printed on the bill

Same number, written with and without spaces. Jev should answer close to 1. Same truck

  • A stronger version. If your system already knows which truck was sent on the trip, put that number in the request as text and ask whether the plate shows it. Then each image is checked against your own record rather than just against each other.
  • Decide the middle ground. Treat a high probability as a match and a low one as a mismatch. Anything in between, such as a hidden or blurry plate, goes to a person.
  • Cost. One extra request per photo-and-bill pair, carrying both images.
Idea 3

Teach by example

What it checks
The same bill-or-photo question as now, but each option is shown with a few real example images as well as described in words.
Why it helps
Words like "weighment slip" may not cover every layout you'll see: another weighbridge's slip, a different GPS camera app's stamp, a slip photographed at an angle. Examples show Jev what you mean. TypeSafe documents this as "define options by example".
How it works
Each option in kind gets a description plus a list of example images.
"kind": Choice(
    instructions="What is `image`?",
    criteria={
        "bill": {
            "description": "A printed bill, receipt or weighment slip.",
            "examples": [Image(Path("examples/bill-1.jpg")), Image(Path("examples/bill-2.jpg"))],
        },
        "geotagged_photo": {
            "description": "A photo with a GPS stamp printed on it.",
            "examples": [Image(Path("examples/geo-1.jpg")), Image(Path("examples/geo-2.jpg"))],
        },
        "other": "Any other photo or document.",
    },
)
On your samples

Your bill and truck photo can be the first examples for bill and geotagged_photo. They must then be left out of testing: an image checked against itself always looks right, so test with different images.

  • Only add this if it's needed. Run the plain version on a batch of real images first. If the type answer is confident and correct, examples add cost for nothing.
  • Every example is sent with every request. Examples count toward the tokens you pay for and the 32 MiB request limit each time. Keep it to one to three small images per option.
Idea 4

Use the original photos

What it checks
Not a check of its own. It changes what goes in: the photo file straight from the phone's camera, not a screenshot or a forwarded copy.
Why it helps
Two reasons. The original has far more detail for reading small print. And it still holds the phone's own GPS location and capture time, which your code can check independently.
How it works
Read the GPS data and capture time from the original file yourself, before sending it to Jev. Jev never sees this data, because the API removes it.
from PIL import Image
from PIL.ExifTags import IFD

exif = Image.open("IMG_1234.jpg").getexif()
gps = exif.get_ifd(IFD.GPSInfo)            # empty if the file has no GPS data
taken = exif.get_ifd(IFD.Exif).get(36867)  # capture time, e.g. "2026:10:15 04:09:12"
On your samples

Size346 × 588 pxabout 4000 × 3000 px

GPS and capture time in the fileNoneUsually kept, if location is on in the camera

The original could be checked twice: the file's GPS against the plant's known location, and the file's capture time against the time printed on the stamp.

  • Messaging apps remove this data. WhatsApp and most chat apps shrink photos and delete GPS data when forwarding. Collect photos through a direct upload instead.
  • It isn't proof either. File data can be edited too. It's one more signal that has to agree with the others, which makes faking harder.

Putting the checks together

Each check gives one of three results, and a trip passes only when every check passes.

Pass

Every check passed with confident readings. Approve automatically.

Review

At least one reading was unsure, for example a blurry plate or faint print. Send to a person.

Fail

A confident mismatch: wrong date, a time outside the window, or a different truck. Flag it.
